# Agent Note: 项目成员只在持久化提交点发布状态

Status: implemented

[English](2026-08-27-project-membership-commit-point-rollback.md) | 中文

## Problem

文件版项目成员 Provider 过去先把每个变更批次落进内存权威表,再等待整体文档写盘。被拒绝的持久写入因此把已生效的批次滞留在内存:读取回答的是持久文档从未接受的行,去重门控对着幽灵行拒绝重试,而下一次成功的变更会把残留序列化进文档——把某次提交早已拒绝的状态发布上盘。一次持久化故障悄悄变成了持久数据。

## Decision

每次变更都在其持久化提交点提交。操作先应用自己的批次,随后 `commit` 等待整体文档的 `writeFileAtomic`;写盘失败时,在拒绝返回前执行该批次的确切逆操作——新增的行被删除,旧角色与标签被还原,已落定的邀请被撤回到 pending 拼写。单一写链使已应用的批次在该点之前不可见,因此逆操作还原出与调用前完全一致的状态,读取、重试与后续文档都表现得像这次调用从未发生。每个批次只陈述一次,即代码本身加上其逆操作闭包;不存在会漂移的平行文档增量表示。该权威在[项目成员服务接缝](../feature/2026-08-27-project-membership-core.zh.md)之后的 placement 不变。

## Verification

执行器套件用目录替换环境文档来注入重命名失败,然后对项目创建、邀请,以及接受/拒绝/撤回/角色/标签/移除全家系要求:调用方收到拒绝;读取与重试同"调用从未发生"无法区分(被拒邀请可重新邀请而非报 `DUPLICATE_INVITEE`,被拒创建的名称可复用);且随后一次成功提交序列化的恰好是已落定的行,不含任何幽灵行。

## Alternatives considered

**先构造变更后的完整持久化文档,写盘成功后才把变更落到内存。** 已拒绝:每个操作要把批次陈述两遍——一遍作为文档增量,一遍作为权威表更新——恰好让缺陷背后的漂移面翻倍。

**失败时从全量状态快照还原。** 已拒绝:每次变更为守护一个批次而深拷贝全部项目、成员与邀请,而逆操作闭包既精确又零拷贝。

## Consequences

持久化故障只表现为该次调用的拒绝;在每个提交边界,内存与磁盘持有完全相同的行。盘上 `rosterVersion` 依旧携带提交时刻的版本,因为发布仍随在持久化之后——已测的一次提交滞后不变。失败的写入不会给写链的下一次提交留下任何可序列化的残留。
