# `@deepseek-ai/dsh-platform`

English | [中文](README.zh.md)

[Product releases](../../docs/product-releases.md) defines Platform version selection, immutable image identity, coordinated promotion evidence, and recovery; this page owns the production deployment transaction.

Platform listen process packaged as a container. GitHub Actions builds the image for pull requests that touch the Platform tree and for matching master pushes. Publishing to GHCR requires an explicit Platform Image call with **push**. Production accepts only the recorded full OCI digest bound to the image build's full candidate commit; tags, short digests, `latest`, and candidate-mismatched metadata are rejected. Secrets come from GitHub Environment `production` at deploy time and are never stored in image layers.

The operated listen process and product clients accept one production identity. `PLATFORM_ORIGIN`, the fixed callback, GitHub client id and credential reference, PostgreSQL database identity, identity namespace, Redis ACL identity, Relay Redis key prefix, a Base64-encoded ApsaraDB CA chain, explicit `PLATFORM_REMOTE_ATTACHMENT_STORAGE`, and the OSS endpoint, bucket, ECS RAM role, object prefix, and timeout are mandatory; there is no development, staging, or default identity. Deployment validation requires an Alibaba Cloud region, OIDC provider and deploy role ARNs, ALB server group and HTTPS listener ids, upload endpoint and object prefix, and exactly two distinct ECS instance ids before a candidate starts.

Account, Project Membership, Personal Pairing, and encrypted attachment HTTP routes admit exactly the production Platform origin plus the shipped Capacitor origins `https://localhost` and `capacitor://localhost`. They echo only the matching configured value, reject opaque `Origin: null`, and never accept a request-provided origin, wildcard, suffix, or arbitrary localhost port.

`GET /` serves the Gestalt and 獭子哥 product homepage from `public/index.html`. Its raw HTML carries the canonical product identity, social metadata, and structured data; `public/robots.txt`, `public/sitemap.xml`, and `public/llms.txt` provide origin-root crawler and agent discovery. A keyless real-Chromium snapshot boots the homepage through the Loader-composed webserver and static host, then pins the title, product links, social preview image, discovery responses, and both language states. The Docker image copies the complete `public` directory. `GET /healthz` and `GET /readyz` answer `{ ok: true, attachmentStorage, instanceId }` after required deployment secrets are present; production assigns each backend a deployment ordinal `instanceId` that contains no network address. Missing or inconsistent identity, Relay, OSS, TLS, `PORT`, or `PLATFORM_LISTEN_HOST` configuration fails before a durable resource is acquired; the listen host is either `0.0.0.0` or `127.0.0.1`. The executable calls `launchOperatedPlatform`, which owns validation, transactional PostgreSQL and Redis acquisition, storage-mode-specific attachment setup, migrations, GitHub OAuth, Account HTTP, Project Membership HTTP, health routes, and quiescent teardown. `postgres` mode never creates an OSS client; `oss` mode uses the ECS RAM-role client. Each Redis owner keeps an error listener while active, destroys a client whose connect fails, and removes the listener after failure or close. Concurrent `SIGINT` and `SIGTERM` requests share one shutdown; the process exits only after HTTP and durable-store owners close, while a close failure is reported and produces a nonzero exit. `OperatedRemoteAccessResources` constructs the PostgreSQL Personal Pairing authority and Relay route stores with the Redis Relay coordinator before listen. Account HTTP is mounted on `/v1/account/*` and Project Membership HTTP on `/v1/projects`. Pairing HTTP and Relay WSS are mounted on `/v1/remote-access/personal-pairing` and `/v1/remote-access/relay`; PostgreSQL owns durable pairing and credential-digest authority, while Redis owns only expiring attachment directories and content-free or ciphertext coordination. File-backed Project Membership state lives at `<storagePath>/production/project-membership.json`, where `storagePath` is `PLATFORM_MEMBERSHIP_STORAGE` or `/var/lib/dsh/projects`; the image declares that directory as a `VOLUME`, the host script mounts named volume `dsh-platform-membership` on the long-running container, and the single-process writer limitation is documented in [the core package](../../packages/platform/project-membership-core/README.md). Platform provides no product pairing cipher and never receives endpoint private keys or a Mobile Relay bearer.

The operated Relay provider uses the same PostgreSQL Personal Pairing authority as its Mobile presence sink. Attach, heartbeat, ciphertext access, and close therefore project lease-derived online state across either ECS instance.

Publish: Actions → Platform Image → Run workflow → set **push**. Deploy: Actions → Platform Deploy; the workflow validates Environment `production`, assumes a least-privilege Alibaba Cloud role from the protected GitHub Environment through OIDC, and verifies Cloud Assistant on both private ECS instances. The role's `MaxSessionDuration` must be at least 21,600 seconds; the credential action rejects a lower limit before any ECS operation. Every deploy and recovery OSS CLI call supplies the configured region and endpoint, so the runner's local profile is not deployment authority. The workflow requires the production ALB server group to contain exactly those two available instance ids on port 80, and requires the named HTTPS listener idle timeout to be at least the Relay heartbeat timeout. It applies the image only when **deploy** is set. The single-line `PLATFORM_APSARADB_CA_BASE64` secret is decoded and validated before resource acquisition, then PostgreSQL and Redis use that chain for CA and hostname verification without relying on the runner or image trust store. The runner uploads the image, an encrypted runtime environment, and the host script to a private, run-scoped OSS prefix; six-hour internal signed URLs let Cloud Assistant fetch them without an ECS EIP or GitHub credential, and the workflow deletes all three objects when the job exits. Cloud Assistant commands are temporary, checked through their terminal invocation status and exit code, and never use public SSH. Image preparation has a thirty-minute limit, ordinary actions have five minutes, and rollback or recovery has thirty-five minutes so it can wait behind an active preparation lock; the freshly acquired six-hour OIDC session exceeds the bounded remote transaction. Every host action holds an instance-local deployment lock, so an error or runner termination can enqueue rollback without racing an active action. A private stable OSS record binds the ordered ECS targets and marks the transaction `rollbackable` until public ALB readiness succeeds, `commit-pending` while rollback containers are removed and attachment authority cuts over, and `committed` after cutover. If a runner disappears, dispatch Platform Deploy with **recover**: a fresh OIDC session first refuses changed target variables, then restores predecessors, finishes cutover, or completes final cleanup according to that record, waits behind the same host lock, and removes the record and run artifacts only after both instances resolve. Select `postgres` for the first atomic-bridge deployment; after it completes on every instance, run the workflow again with `oss`. Each invocation starts and checks every loopback candidate, then replaces one instance at a time while the other remains available. Each predecessor receives SIGTERM with a sixty-second graceful deadline. A rolling failure restores every available rollback container. After both replacements are locally healthy, the workflow uses pinned Node 24 to reach the production HTTPS `/readyz` route through the WAF-enabled ALB and verifies the selected attachment storage plus both expected non-sensitive instance ids before removing rollback containers. Public DNS, TLS, ALB, sticky routing, or backend-group failure therefore fails the deployment while rollback remains available. The workflow then removes every stopped rollback container before committing the deployment-wide attachment authority transition; cleanup failure leaves one active image generation in the prior compatible phase. ECS publishes host port 80 to the container listen port 8080 so ALB HTTPS:443 can forward to VPC:80. The apply step uses Docker `json-file` rotation (`20m` × `3` files) so container stdout/stderr cannot fill the host disk. It also runs LoongCollector (`dsh-loongcollector`) so `dsh-platform` stdout/stderr can reach SLS project `gestalt` logstore `application` in `cn-hangzhou`. Before replacing a running collector, preparation pulls the fixed collector image or verifies that exact image is already cached; a registry outage therefore keeps the current collector until a usable image exists. The collector registers with user-defined machine-group id `gestalt-platform` and reads the Aliyun account id from hardened ECS metadata, falling back to `PLATFORM_SLS_ACCOUNT_ID`. Bind that group to the logstore's Docker stdout Logtail config. Runtime secrets remain in Environment `production`; the repository and image contain none.

The deployment supplies a distinct `PLATFORM_RELAY_INSTANCE_ID` per ECS host plus positive capacity, acknowledgement, directory TTL, heartbeat timeout, ciphertext buffer, connection, pending-delivery, and attach-timeout values through the `PLATFORM_RELAY_*` variables. PostgreSQL owns one-time attachment capability digests, pairing ids, publish intents, private OSS object keys, byte lengths, expiry, branded Account quota reservations, shared bridge/OSS consume claims, and capacity; the private OSS bucket owns ciphertext bytes without receiving endpoint keys or plaintext. Upload requires a positive exact `Content-Length`, reserves quota before reading the body, and commits a publish intent before OSS writes. Finalization atomically replaces the intent with object metadata; expiry reconciliation after a crash deletes an orphan object and releases quota. HTTP consume claims authority before the response, restores an unexpired claim after a failed or prematurely closed body, and admits only one bridge/OSS response. Consume, revoke, expiry, and pairing revocation commit metadata removal and quota-release work before object cleanup; a configured periodic sweep deletes only explicitly inactive candidates and queues bulk deletion with bounded concurrency, while disposal waits for active work. A one-day lifecycle rule scoped to `PLATFORM_OSS_OBJECT_PREFIX` recovers an object whose direct cleanup failed. Every durable read validates digest length, branded pairing id, exact object-key binding, bounded byte length, safe-integer expiry, claim, and quota reservation before the row reaches product authority; OSS download validates authoritative length before allocating one buffer and destroys the stream on failure. Attachment HTTP authenticates the current Mobile Installation and exact confirmed pairing selector; the selector alone has no authority.

## Certificate renewal

`.github/workflows/platform-certificate-renew.yml` validates the operated certificate on demand and checks daily whether renewal is due. It assumes the existing production Alibaba Cloud role through GitHub OIDC; no Alibaba Cloud AccessKey or local OAuth state is used. The workflow verifies an immutable acme.sh source archive before execution, keeps its temporary home owner-only, and stores the ACME account and certificate state as an AES-256 encrypted object in the existing private deployment OSS bucket. The encryption key remains a protected GitHub Environment secret and is never written to OSS or repository files.

A scheduled run exits without issuance until the active ALB certificate enters the thirty-day renewal window. Renewal uses an OIDC-native AliDNS hook, removes every challenge record on success or failure, and uploads a certificate only after its private key, exact apex/www SAN set, and minimum lifetime pass validation. It then changes only the configured ALB listener certificate, verifies both ALB addresses with ordinary TLS validation, and retains the prior certificate for rollback. `workflow_dispatch` defaults to `validate`, which verifies the pinned client, encrypted state access when present, current certificate consistency, TLS endpoints, and cloud read authority without issuing or changing a certificate. GitHub reports a failed scheduled job; operators must treat a failure inside the renewal window as expiry-alert evidence.

Required non-secret production variables are `PLATFORM_CERT_DOMAIN`, `PLATFORM_CERT_WWW_DOMAIN`, `PLATFORM_CERT_ALB_EIPS`, `PLATFORM_CERT_ALB_LISTENER_ID`, and `PLATFORM_CERT_STATE_OBJECT`. `PLATFORM_CERT_STATE_KEY` is one random protected Environment secret used only for client-side state encryption. The deploy role adds only challenge-record operations for the operated domain, certificate upload/read, this listener's certificate update/read, and Get/Put access to the exact state object; it retains the old listener and certificate for rollback.

## Known Limitations and Deferred Work

- Redis and PostgreSQL certificate verification cannot be disabled by product configuration. The product-entry test drives `launchOperatedPlatform` with disposable non-TLS store adapters after validating the operated TLS configuration; it is not live operated acceptance.
