# `@deepseek-ai/dsh-remote-access`

English | [中文](README.zh.md)

Remote Access Service Definitions and Personal Pairing Service Provider. `ctx.remoteAccess` keeps Mobile Access disabled per Desktop Installation until Settings enables it, creates two-minute single-use invitations, authenticates each Account Session's Installation id, kind, and Mobile presentation through `AccountService.currentInstallation()`, requires both Installations to resolve to the same Account, and grants a Device Principal only after explicit Desktop confirmation. Pairing completion carries no caller-supplied device metadata; pending and confirmed records copy the authenticated Mobile Installation presentation. Open-registration quotas cap installations, pairings, and blobs; capacity watermarks reject new login, pairing, blob, or WSS attach with `PLATFORM_CAPACITY` and `retryAfter` while established ciphertext streams continue. `createChallenge` requires a non-empty client IP; Pairing Challenge HTTP supplies the TCP peer address and ignores `x-forwarded-for`. Hourly challenge, concurrent blob, and daily upload windows live in the shared pairing-transaction state, so two providers with one `PersonalPairingAuthorityStore` enforce one Account-complete limit. Hard caps return a 60-second `retryAfter`; sliding windows return remaining-window seconds. `admitAttachmentBlob` / `releaseAttachmentBlob` enforce the blob ceilings by declared size without storing ciphertext. Development and production keep separate origins, OAuth Apps, callbacks, credentials, databases, and identity namespaces; secrets come from deployment-managed references and fail closed when missing. `PersonalPairingAuthorityStore` atomically owns the shared Desktop access-to-route association, confirmed Mobile pairing result, and those quota windows; the memory adapter is only for keyless tests, while a deployment supplies one durable adapter to every Platform Instance.

The QR payload and full one-time HTTPS link are identical and carry a 256-bit invitation secret, Desktop fingerprint, rendezvous id, expiry, and protocol major. A completed handshake remains pending while both installations display the same six authentication words derived from its handshake hash. Expiry, cancellation, account mismatch, rejection, successful completion, and disablement destroy the corresponding crypto-provider capability. A completion id replays only when a retained SHA-256 commitment matches the Account, Mobile Installation, every invitation field, and Mobile handshake bytes; changed request content fails as an id collision. The shared transaction document uses format version 1. An unversioned document retains digest-bound replay and confirmed pairings; completion or pending records without a digest become non-replayable terminal cleanup records. Unknown explicit versions and malformed versioned records are rejected. Confirmation ids make confirmation retries idempotent, and serialized mutation gives one concurrent completion the invitation.

Terminal state is committed before provider cleanup. Failed challenge or pending-key destruction remains in a retryable cleanup record, while client retries observe the original completion, confirmation, cancellation, rejection, or expiry result without repeating a handshake or activation. Each authenticated Installation may own at most four live challenges, four pending pairings, and sixteen total live or replay-retained lifecycle records. Cleaned replay projections expire after five minutes, while cleanup-failed tombstones retain capacity until destruction succeeds; an orphaned pending key is charged to both owning Desktop and Mobile Installations without duplicating a settled record. Expiry is scheduled when a challenge is created. Shared-authority disposal still settles this instance's live challenges so they cannot pin the per-installation cap after the creating process is gone. Provider disposal drains instance-local incomplete work but preserves confirmed pairing and route authority so rolling replacement can reconnect; explicit disable owns durable revocation. Generated opaque-id and key-reference collisions fail without replacing retained records; an activation allocation becomes cleanup-owned before its public reference or generated ids are parsed.

`PairingHandshakeProvider` is the only cryptographic adapter. The package does not implement Noise. `DevelopmentKeylessPairingHandshakeProvider` derives a SHA-256 pairing key only for explicit development compositions; production compositions must not import it and never select it. Each activation returns a public branded key reference and a distinct provider-private allocation handle; rollback destroys only that new allocation and cannot address an existing pairing's key. A confirmed pairing seals Mobile-specific Relay authority to that pairing key before the shared store publishes the paired result. Mobile opens that value through its crypto adapter, configures its own Relay lifecycle, and never receives or reuses the Desktop Relay credential. The resulting Device Principal has only `companion-surface` authority. The HTTP Consumer and shared HTTP transport connect `ctx.remoteAccess` to the Desktop Settings and Mobile controllers. Mobile retains an unsent prepared completion until invitation expiry, a possibly committed request for the server replay window, and a pending result until an explicit terminal decision. Every retry reuses its completion id and handshake bytes. Account changes await the previous account's Companion release and Relay revocation before activation continues. Unpair attempts handshake, pairing-key, Companion, and Relay cleanup independently and reports all failures. Mobile publishes the unpaired ready state only after every cleanup succeeds; a rejection remains an explicit retryable failure, is reported by the React owner, and never claims authority was removed. Both controllers stop timers, drain in-flight work including browser-camera scanning, and reject pairing verbs after sign-out or unmount. The Loader example runs that controller/HTTP path with `DevelopmentKeylessPairingHandshakeProvider`; it is not product cryptography.

`ctx.remoteRelay` owns the stateless multi-instance Relay lifecycle. A 32-byte rotatable Desktop credential is hashed before the persistent `RelayRouteStore`; confirmed Mobile endpoints receive separate issued credentials at the same route revision, and the opaque route id alone cannot attach. The Personal Pairing authority binds a content-free credential fingerprint to the confirmed device. Each authenticated Mobile attachment records its connection token and expiring lease; attach, heartbeat, and ciphertext access advance `lastAccessAt`, while close removes only that token. Presence is true when any current lease remains, so a stale close cannot clear a replacement and a crashed process becomes offline at lease expiry. Desktop Settings reads this state rather than a fixed confirmation-time value. Each Platform Instance authorizes an attachment, flushes ready, then registers it in an expiring shared directory and publishes directly to the target instance. Cross-instance events contain only bounded Relay ciphertext, branded transport ids, connection tokens, and route revision. A missing target returns `REMOTE_OFFLINE`; there is no offline ciphertext or mutation queue. Capacity sheds only new attachments, slow consumers are disconnected at a configured byte bound, heartbeat revalidates route authority, and rotation or revocation invalidates older live attachments across instances. The host-only `relay-provider` bundle imports `RemoteRelayError` from this package's public entry so HTTP Consumers that map that class share one constructor.

Persistent deployment state is limited to route identity, credential digest, monotonic revision, and revocation/association state. Ephemeral coordination is limited to expiring attachment locations, invalidation events, and direct ciphertext Pub/Sub. Instance exit closes its sockets; Mobile and Desktop acquire a fresh non-sticky connection, and Desktop sends an authoritative encrypted resynchronization instead of migrating a live socket. Every capacity, directory, heartbeat, buffer, connection, and attach timeout is an explicit validated composition value.

None.

## Known Limitations and Deferred Work

- Production activation remains fail-closed until an independent reviewer accepts the Snow proof and a reviewed `PairingHandshakeProvider` is assembled.
- Personal Pairing challenge and pending-handshake records still use the checked-in single-process provider. Confirmed pairing-to-route/access authority and the Relay route store are deployment-owned seams; this repository does not provision PostgreSQL, Redis, TLS, or cloud instances.
- Relay transport availability does not approve product encryption. Production Desktop composition remains fail-closed until the independent Noise gate admits a reviewed handshake and Companion channel provider.
