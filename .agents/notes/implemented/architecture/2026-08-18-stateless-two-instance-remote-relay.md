# Agent Note: Route paired endpoints through stateless Platform Instances

Status: implemented

English | [中文](2026-08-18-stateless-two-instance-remote-relay.zh.md)

## Problem

Mobile and a paired Desktop may reach different Platform Instances behind one non-sticky endpoint. A route id cannot be sufficient attachment authority, and Platform must not receive DSH Session, prompt, approval, model, Workspace, or other Companion business values. Rolling replacement must recover without migrating a live socket or retaining an offline mutation. Desktop process lifecycle must also remain the truth for whether the remote endpoint is online.

## Decision

Remote Access owns a `ctx.remoteRelay` capability separate from the [Relay Transport and encrypted Companion protocols](2026-08-18-versioned-remote-protocol.md). `RemoteRelayProvider` is stateless with respect to deployment data. Every instance receives the same `RelayRouteStore`, `PersonalPairingAuthorityStore`, and `RelayCoordinator` interfaces plus an opaque branded instance id and explicit validated limits. The authority store atomically owns Desktop Mobile Access, its active route, pending route-revocation tombstones, and confirmed Mobile pairing results. A 32-byte canonical base64url Desktop Relay credential is generated with a cryptographic entropy source, returned only to the Desktop authority, hashed before persistence, and rotated by monotonically increasing route revision. Each confirmed Mobile pairing receives a separate credential at that current revision, sealed to its pairing key before Mobile observes confirmation. Attach requires both the route id and one current credential. Rotation and revocation fan out a content-free invalidation and close older local attachments.

The minimum persistent authority contains the Desktop Installation association, active or revoking route identity, credential digests, monotonic revision, revocation state, confirmed Personal Pairing identity, and sealed Mobile Relay authority. It contains no plaintext Companion or Harness value and no Desktop credential. The Redis coordinator owns only ephemeral expiring directory entries, direct instance Pub/Sub, and invalidation. Directory entries contain route and attachment ids, endpoint kind, Platform Instance id, a stale-cleanup-safe connection token, revision, and expiry. Conditional Lua refresh and unregister compare the connection token. Pub/Sub events contain the bounded Relay ciphertext frame plus target connection token and revision. Subscriber count does not prove delivery: a bounded content-free acknowledgement, correlated by an opaque collision-checked id, succeeds only after the target attachment accepts the frame. Redis Streams, Lists, and other offline queues are not used.

One exact WSS Consumer requires an attach frame before any ciphertext or heartbeat, disables compression, applies the protocol frame ceiling and a validated attach timeout, serializes frames, and flushes ready after authorization and before directory registration so a peer cannot locate the attachment until the endpoint has seen ready. Its lifecycle signal cancels route authorization and directory registration when the deadline, socket, or Consumer closes. Admission reserves capacity across asynchronous authorization, revalidates after registration to close rotation and revocation races, and cannot outlive provider disposal; invalidation needs no retained global route history because every admitted connection is inserted before the final authoritative revalidation. A missing or expired target, absent instance subscriber, stale target rejection, delivery-ack timeout, disconnected endpoint, or offline send returns `REMOTE_OFFLINE`; nothing is retained for replay. Per-instance capacity rejects only new attachments with a retry delay. Per-target buffered ciphertext bytes are bounded; exceeding the limit disconnects the slow consumer. Heartbeats revalidate the credential digest and revision, conditionally refresh the directory, and expire attachments that stop proving liveness. Every termination path retains a retryable cleanup tombstone and its capacity until socket, writer, directory, pending acknowledgements, and subscription cleanup succeed.

Mobile and Desktop acquire outbound connections through the deployment's single non-sticky TLS endpoint. Client sockets enforce the wire ceiling and feed item-and-byte-bounded live queues; stop aborts and settles credential acquisition plus DNS/TLS connection work. Physical socket loss starts a new acquisition after a validated delay. Desktop supplies a mandatory authoritative encrypted resynchronization callback after every successful ready acknowledgement, so rolling replacement rebuilds state instead of migrating a live socket. The endpoint controller rejects misrouted ciphertext and never retains an offline mutation. Desktop Settings starts Relay only while Mobile Access is enabled; window close drains Relay before destroying the window, and sleep, quit, sign-out, or disabling Mobile Access stops and drains the connection. No daemon, background Host, or remote wake path exists.

The long-running Account, pairing, and Relay listen consumed by Mobile and Desktop product entries is [`examples/local-companion-platform`](../../../../examples/local-companion-platform/README.md). The assembled keyless scenario runs one real local TLS/WSS listener that non-sticky dispatches successive connections to two in-process Platform backends using the shared coordinator contract. Public Remote Access operations enable the Desktop route, confirm a pairing, seal a distinct Mobile credential, and recover that result from another Personal Pairing provider before either endpoint connects. Mobile and Desktop deliberately land on different instances, complete one encrypted Companion round trip, dispose the first Personal Pairing provider without revoking durable authority, replace the Desktop Relay instance, and verify Mobile decrypts the Desktop-authoritative revision after reconnect. A replacement provider then disables the shared authority and the route becomes offline. The scenario also proves an offline target yields `REMOTE_OFFLINE` with zero retained ciphertext. A separate disposable `redis-server` integration executes the maintained adapter's Lua, reads key TTL and replacement value, verifies stale unregister cannot delete the replacement, and checks no Stream or List exists. The scenario's harness-only AES-GCM channel, keyless authority serializer, and test certificate do not enter production. The independent Noise security gate continues to keep production pairing and Relay activation fail-closed; explicit development Desktop and Mobile configuration can assemble the real WSS lifecycle without claiming a product Companion crypto provider.

## Alternatives considered

**Use load-balancer stickiness.** Sticky routing hides instance ownership in edge state and does not survive rolling replacement. The shared expiring directory makes every connection and every instance disposable.

**Use a durable broker queue.** Queuing ciphertext would create offline delivery semantics, retention, replay, deletion, and product policy not required by Remote Companion. Direct Pub/Sub reports the live miss immediately.

**Store Companion objects in Platform.** Parsing or persisting application values would collapse the protocol separation and expose DSH authority to the centralized service. Platform forwards only the already bounded ciphertext envelope.

**Run a background Desktop Host.** A daemon or remote wake path would make window state misleading and add a new installation lifecycle. Closing the only Desktop window instead exits the process and makes the route offline.

**Integrate proof-local Snow code.** Transport delivery does not authorize product cryptography. The reviewed provider remains an independent gate, and the executable acceptance scenario stays explicitly keyless.

## Consequences

Two Platform Instances can share one endpoint without connection affinity, and rolling replacement loses only ephemeral sockets. Instance disposal does not revoke confirmed pairing or route authority; explicit disable moves the active route into a durable revocation tombstone and any later enable uses a replacement route that stale cleanup cannot remove. Route ids remain non-secret locators, credential rotation and revocation have cross-instance effect, and the coordinator cannot inspect Companion business values. The trade-off is that endpoint reconnection and Desktop resynchronization are required after every instance loss, while offline Mobile work fails immediately and must be retried by an explicit future product action rather than infrastructure replay. Cloud provisioning, production TLS certificates and edge configuration, Redis availability, and the reviewed product cryptographic provider remain deployment work rather than claims of this repository. Production listen migrates PostgreSQL pairing-authority and route-store tables through [`PostgresPersonalPairingAuthorityStore`](../../../../apps/platform/src/postgres-pairing-store.ts) and [`PostgresRelayRouteStore`](../../../../apps/platform/src/postgres-route-store.ts); pairing HTTP and Relay WSS stay unmounted until that handshake is approved.
