# Agent Note: 主 CI 使用标准 GitHub 托管运行器

Status: implemented

[English](2026-08-18-standard-hosted-primary-ci.md) | 中文

## 问题

拉取请求 CI 在作业解析到未配置的自定义运行器标签时无法产出结果。三个主要 Linux 作业和独立的原生 Windows 作业使用仓库中不存在的大型运行器标签，因此即使标准 GitHub 托管容量可用，它们仍会持续排队。

## 决策

三个主要 Node 24 Linux 作业默认解析到 `ubuntu-latest`，原生 Windows 作业默认解析到 `windows-latest`。对于可信且非 Dependabot 的拉取请求，仓库变量 `DSH_CI_FAILOVER_LINUX` 和 `DSH_CI_FAILOVER_WINDOWS` 仍可选择各平台的自托管池。[故障切换手册](2026-07-26-ci-failover-runbook.md)负责该操作。

标准运行器的默认值会限制进程扇出：Linux 静态检查使用 4 个顶层工作进程，覆盖率检查使用 2 个顶层工作进程和 2 个插桩工作进程，consumer 检查使用 4 个顶层工作进程和 8 个快照工作进程，原生 Windows 使用 1 个顶层门禁工作进程、1 个覆盖率工作进程和 1 个 publint 工作进程（[串行门禁决策](2026-08-23-hosted-windows-serial-gates.md)）。自托管分支保留其运行器池专属的内部工作进程上限。

自定义大型运行器标签只保留在手动派发的基准测试矩阵中。[CI 工作流测试](../../../../scripts/ci-workflow.spec.ts)要求拉取请求作业默认使用标准标签，并拒绝这些选择器中的自定义大型运行器标签。

## 考虑过的替代方案

**默认使用自定义大型运行器。**大型运行器在已配置时可以缩短耗时，但缺失的自定义标签会让所有匹配作业持续排队且无法得出结论。手动基准测试保留性能比较路径，同时不再让自定义资源分配成为拉取请求的前置条件。

**默认使用自托管运行器。**这可以避开自定义托管标签，但会让公司自有机器成为主要可用性依赖。显式的平台开关在事故期间仍可使用自托管容量，而不会把它放在正常路径上。

**排队超时后自动回退。**GitHub Actions 在排队前解析 `runs-on`，等待后不会把作业重新求值到另一个标签。因此，恢复操作需要在修改相应仓库变量后发起一次新运行。

## 后果

拉取请求 CI 无需仓库专属的大型运行器配置即可启动，代价是 Linux 和原生 Windows 在标准机器上的执行时间更长。已经按旧自定义标签排队的作业不会重新定向；包含标准选择器的工作流可用后，必须取消并重新触发这些作业。

标准运行器的首次执行还暴露了既有的模块图漂移，以及已提交 Noise 安全证明中未声明的外部二进制。生成的模块图现已同步；证明工具生成的 TypeScript 声明已从未使用源码分析中排除，其由环境提供的构建工具也登记为忽略的二进制；切换运行器池不会削弱静态门禁。
