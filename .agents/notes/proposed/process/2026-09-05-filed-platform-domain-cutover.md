# Agent Note: Filed-domain Platform cutover to beikejiedeliulangmao.top

Status: proposed

English | [中文](2026-09-05-filed-platform-domain-cutover.zh.md)

## Problem

The operated Platform serves `https://www.gestaltrun.com/` from `apps/platform/public` through one ALB HTTPS listener while the gestaltrun.com ICP filing is pending. A filed domain, `beikejiedeliulangmao.top`, is now approved under 辽ICP备19017854号-1 for the authenticated Aliyun account that operates the deployment. Until the origin moves onto the filed domain, production service in mainland China carries filing risk on the current name.

Moving the origin is not a single DNS edit. `PLATFORM_ORIGIN` in Environment `production` is the input the Desktop config writer, the Mobile build, and the Platform listen process all derive their identity from: the Desktop config writer derives the Relay WSS URL as `wss://<origin>/v1/remote-access/relay`, the Mobile bundle bakes `VITE_PLATFORM_ORIGIN`, `VITE_PLATFORM_CALLBACK_URL`, and `VITE_REMOTE_RELAY_WSS_URL` at build time, the Platform listen process derives CORS allowed origins and the `/pair` link origin from the same value, and `production-env.ts` enforces that `PLATFORM_ORIGIN` and `PLATFORM_GITHUB_CALLBACK` share one HTTPS origin with callback path `/v1/account/oauth/github/callback`. Installed Desktop clients and published Mobile builds carry the old origin, and the GitHub OAuth App's callback URL is registered outside the repository.

#480 records that the current ALB/TLS boundary rejects Android System WebView 83 with `net_error -101`. The cutover changes the TLS certificate presented at that boundary, so #480's diagnosis must be revalidated against the new-domain certificate rather than carried over as either evidence or blocker. #415 tracks a release-train alignment and stays open until its own release evidence completes.

The user has also explicitly requested monthly-subscription ECS at the cheapest sufficient configuration and savings elsewhere including the load balancer, so the migration scheme must carry a required cost right-sizing dependency instead of assuming the current topology — two ECS instances behind an ALB — is fixed. What the cost decision may not touch is the durable substrate: identity, database, and data.

Old-client transition has been verified in code rather than assumed. The login POST carries installation identity only (`packages/platform/platform-account-client/src/index.ts` — `beginLogin` sends `InstallationLoginIdentity` + public key); the server generates the GitHub `authorizationUrl` with its own configured `redirect_uri` and fixed callback (`packages/platform/platform-account-core/src/index.ts` — `authorizeUrl` builds `https://github.com/login/oauth/authorize` with `client_id`, the environment's `callbackUrl`, `state`, and the S256 code challenge); the client-side parser validates only an HTTPS scheme on the returned `authorizationUrl` (`packages/platform/platform-account/src/parsers.ts` — `parseLoginAttemptView` requires `httpsUrl(record.authorizationUrl)`). Consequence: old clients can keep POSTing login attempts and polling on the old hostname while the server emits new-domain OAuth callbacks, provided both hostnames reach the same backend with the same identity; the Environment origin change does not shut the old hostname down; and no second OAuth App is required.

## Proposal

Cut the operated Platform over to `https://www.beikejiedeliulangmao.top` with apex (`beikejiedeliulangmao.top`) support, through the staged sequence below. The user has confirmed the canonical www origin and already authorized both the domain deployment and the formal Desktop/Mobile reissue; those proceed without re-asking blanket approval per step. What still awaits explicit user approval, each on its concrete evidence, is narrower: the specific pending quote and purchase for the selected ECS shape, plus any other quoted spend (renewals, billing-model changes), any destructive resource change (release, deletion, data-store removal), and any high-availability tradeoff. The user has now explicitly selected the target architecture — two `ecs.e-c1m2.large` (2 vCPU, 4 GiB) instances on monthly subscription, RDS and Redis retained with their billing optimized, and the load balancer retained in a two-node cost-optimized form; the single-node alternative was evaluated and not selected. This note and its PR perform no mutation: the stages are the durable plan the authorized execution follows, and all cloud work stays read-only until the validated cost plan is confirmed.

Canonical authority after cutover:

- `PLATFORM_ORIGIN` (Environment `production`) becomes `https://www.beikejiedeliulangmao.top`; `PLATFORM_GITHUB_CALLBACK` becomes `https://www.beikejiedeliulangmao.top/v1/account/oauth/github/callback`.
- Environment `desktop-release` updates the same two names, `PLATFORM_ORIGIN` and `PLATFORM_GITHUB_CALLBACK` — the Desktop config projection reads `PLATFORM_*` names, not `VITE_*`. Environment `mobile-release` updates `VITE_PLATFORM_ORIGIN`, `VITE_PLATFORM_CALLBACK_URL`, and `VITE_REMOTE_RELAY_WSS_URL` to the same www origin, keeping `VITE_REMOTE_RELAY_WSS_URL = wss://www.beikejiedeliulangmao.top/v1/remote-access/relay` consistent with the Desktop-derived relay URL.
- The GitHub OAuth App (client id `Ov23lip9LTmnFuFpFeeV`) callback URL is re-registered to the new callback path. This App is distinct from the repository's automation GitHub Apps and is not replaced; the code-verified transition requires no second OAuth App.
- Unconditional preservation: `PLATFORM_POSTGRES_DATABASE` (database identity), `PLATFORM_IDENTITY_NAMESPACE`, `PLATFORM_TOKEN_SIGNING_KEY`, `PLATFORM_POLLING_SIGNING_KEY`, and all durable data. Accounts, installations, pairings, and durable state survive because the identity that keys them is preserved. RDS and Redis stay; only their billing is optimized.
- Selected topology (user choice, pending validated totals): two `ecs.e-c1m2.large` (2 vCPU, 4 GiB) ECS instances on monthly subscription replacing the current instances — the user's catalog shows 47.52 per instance per month while the actual disk-inclusive total awaits validation against the 67.52 figure that includes disk; the load balancer is retained with two nodes and its cost optimized; single-node was evaluated and not selected. The migration executes against this shape once the pending quote and purchase are explicitly approved.
- The three TXT records and any other DNS records on the zone are preserved verbatim; only the two old A records (`120.77.49.2`, apex and www) are replaced, with recorded pre-change values for rollback. Both hostnames migrate; canonical authority stays the www origin. The pre-disabled `www.gestaltrun.com` record is not silently re-enabled.
- The gestaltrun.com certificate stays attached and the old hostname keeps serving until old-client transition evidence closes; the old hostname is not retired by the origin switch, and the identity namespace serving it is preserved unchanged.
- Reductions to high availability (single-instance deployment, removal of the load-balancer tier) and every priced purchase (new instances, upgraded specs, reserved or subscription billing) are gated on an explicit user decision per item, taken after the read-only assessment reports actual billing, utilization, and quotes. No order, renewal, spec change, or destructive change is authorized by this note.
- The brand name, READMEs, historical release notes, and docs that reference gestaltrun.com are not renamed. The homepage SEO canonical remains `https://www.gestaltrun.com/` by default pending an explicit decision, because `apps/platform/public/index.html` and its discovery metadata are served on both hostnames and a premature canonical switch would drop the indexed origin before the new domain accumulates standing.

Apex behavior: the apex hostname gets a valid certificate and DNS reachability so that apex HTTPS does not fail, but the canonical authority is the www origin. Whether apex serves a redirect to www, or serves the product directly, is decided during Stage 1 verification after observing listener and certificate behavior on the existing ALB; OAuth POST callbacks and Relay WSS are never pointed at the apex.

## Staged cutover

Stage 0 — Freeze and record (no production mutation). Record current apex/www A values (`120.77.49.2`, TTL 600 s), the three TXT records, the ALB listener id and its current certificates, server group, ECS instance ids, and the current GitHub OAuth App callback URL. Re-fetch `origin/master` and confirm the release-train state (PR #584 / plan 0012 selecting Desktop 0.1.16) so this cutover does not interleave with that train.

Stage 0.5 — Cost plan validation (read-only, then the pending purchase decision). The architecture direction is already chosen by the user: two `ecs.e-c1m2.large` (2 vCPU, 4 GiB) monthly-subscription ECS instances, RDS and Redis retained with billing optimized, and a two-node load balancer with cost optimized — single-node evaluated and not selected. What this stage still validates read-only: the 47.52-per-instance catalog price against the 67.52 figure that includes disk, so the confirmed disk-inclusive total is what the user approves; utilization fit of the 2 vCPU/4 GiB shape against observed load; the load-balancer and NAT cost reductions on quote; and RDS/Redis billing optimization options. The billing-report disagreement is resolved in direction by a timestamped corrected report — balance +86.52 with no ALB financial locks at 2026-09-05T16:04Z — which supersedes the earlier FinancialLocked/−13.48 reading; the rule stands that a current timestamped recheck is taken immediately before any mutation, because account state is time-sensitive input rather than settled fact. The user then approves the specific pending quote and purchase; only that approval releases the corresponding Stage 1/3 mutations — no priced purchase, destructive resource release, or data-store deletion happens before the user sees and confirms the concrete plan and amount. The load balancer is retained, so Stage 1 attaches certificates to the listener as written; only the validated cost differs from the original projection.

Stage 1 — Certificate and DNS (Aliyun console, authorized operator, on the architecture selected in Stage 0.5). When the ALB is retained: issue one HTTPS certificate covering both `beikejiedeliulangmao.top` and `www.beikejiedeliulangmao.top` (DCV on the existing DNS), attach it to the existing ALB HTTPS listener alongside the current gestaltrun.com certificate (multi-certificate listener, not a replacement), then replace only the two old A records so apex and www resolve to the existing ALB front address. When a different frontend was selected: issue the same certificate, terminate it per that architecture's plan, and point both hostnames at it. Preserve TXT records and TTL values in the record. Verify in both cases: authoritative and public DNS resolution for both names, TLS handshake and hostname validation for both names from an ordinary client, and continued gestaltrun.com service during this stage (old certificate still attached).

Stage 2 — Platform origin switch (GitHub Environment `production` only; no deploy yet). Update `PLATFORM_ORIGIN` and `PLATFORM_GITHUB_CALLBACK` vars; re-register the OAuth App callback. Run the platform-deploy validate job (source CLI `production-env-cli.ts` rejects mismatched origin/callback before any ECS apply). Verify `/readyz` on the new www origin against the still-running old deployment before proceeding. This stage is reversible by restoring the two Environment variables and the OAuth App callback URL. The switch changes what new server responses carry: after the deploy that consumes them, login attempts initiated on either hostname receive a server-generated `authorizationUrl` whose `redirect_uri` is the new-domain callback, while the client parser accepts any HTTPS `authorizationUrl`. The switch does not stop the old hostname from serving, and no second OAuth App is created for the transition. Login attempts already pending at cutover time reference the pre-switch callback; they may need a client restart to re-initiate against the post-switch flow, and Stage 5 covers that restart as part of the transition rather than as a service guarantee.

The old DNS records on gestaltrun.com are currently DISABLED — an unresolved deliberate state owned outside this note. This note does not re-enable them: any change to that state is a separate explicit user decision with its own record. While the old hostnames stay disabled, old clients cannot reach the Platform directly; the Desktop updater is independent of the Platform origin (it updates through GitHub Releases), so an installed old-origin Desktop can still update to the reissued release and thereby adopt the new origin even with old DNS down.

Stage 3 — Platform deploy (protected workflow, explicit approval, on the selected architecture). This stage includes the approved ECS replacement to the two `ecs.e-c1m2.large` monthly instances: the platform-deploy dispatch carries the candidate SHA against the new pair, preserving the two-instance rolling replacement, rollback record, and attachment-storage cutover the workflow already owns once the new instances join the server group. Verify account login on the new origin and Relay WSS on the new origin. Old-client behavior is verified in Stage 5, not assumed here: installed clients still pointing at gestaltrun.com continue to reach the dual-cert frontend, but whether their login completes is a Stage 5 evidence question, not a Stage 3 assertion.

Stage 4 — Client reissue (formal Desktop and Mobile releases from one reviewed candidate). Bump Desktop and Mobile versions through a new Product Release Plan on `master`; the new origin is baked into the Desktop operated config and both Mobile builds at that candidate. Desktop publishes through desktop-release (signed, notarized, `--latest`). The user's formal Mobile request is product distribution to Mobile users, which the workflow splits into two separately evidenced channels: the signed Android APK as durable product distribution, and the iOS TestFlight upload as a distinct gated step reported shipped only when `upload_testflight` was requested and a validated build number exists. Neither channel alone satisfies the formal request: a GitHub prerelease by itself is not formal Mobile publication, and the TestFlight upload is a separate product-distribution gate rather than a downgrade of the request. Before any Mobile publication, verify new-domain TLS/readiness from the physical Android path (WebView, not only desktop browsers), because #480's failure lived exactly there.

Stage 5 — Physical acceptance and old-client transition evidence. Phone-side: valid TLS, fresh GitHub login preparation, same-account authentication, WSS attachment, explicit-link pairing, Remote Online, and phone-originated ping/pong — preserving user devices and Desktop instances, with sanitized evidence published through `gif-assets`. Desktop-side: update from an installed old-origin build to the new release through the GitHub updater — which stays reachable because it is independent of the Platform origin — and confirm the reissued channel. Old-client transition is proven here on the verified mechanism, before any retirement of the old certificate: an installed old-origin client POSTs login and polls on the old hostname (when old DNS is enabled) and completes the OAuth flow against the new-domain callback the server generates, or the finding is recorded as a transition gap that blocks Stage 4's claim of a non-breaking reissue. Pending pre-cutover login attempts that fail to complete after the switch are handled by a client restart re-initiating the flow, and that restart requirement is recorded as transition evidence. The gestaltrun.com certificate stays attached and its namespace unchanged until this evidence closes; only an explicit later decision detaches it. Rollback at every stage: Stage 1 restores old A values and detaches the new certificate; Stage 2 restores the two Environment variables and the OAuth App callback; Stage 3 uses the workflow's own rollback record; Stage 4 does not unpublish old releases — old installers remain valid download targets, and rollback is re-pointing origin variables plus reissuing from the prior candidate.

## Sequencing against the in-flight release train

PR #584 carries Product Release Plan 0012 selecting Desktop 0.1.16 from `automation/product-release`, verified read-only at head `3ac00a04805a3415b68a8d4e69d5c45af816c4f3` (OPEN, Draft). That PR is not modified by this specification, and this branch's planning is coordinated against its state without depending on its head moving. The ordering rule is ledger collision, not version dependency: this cutover's Product Release Plan (Stage 4) is created on `master` only after plan 0012 has merged or been explicitly dispositioned, because two open plans over `product-releases/` would contend for `nextSequence` and the release-intent ledger. Beyond that rule the version sequence stays flexible — nothing here requires the Desktop reissue to build on 0.1.16 specifically, and this task does not dispatch #584's release on the basis of an unrelated recommendation: any release dispatch is coordinated against the freshest release-train state by whoever owns that decision, to avoid unnecessary paid or release mutations. Platform-deploy dispatches (Stage 3) do not contend with a Desktop-only plan; if 0012 has already promoted Desktop, Stage 3 may run before or after Stage 4's plan merges, but the mobile acceptance run (Stage 4) must bind to the exact new-domain candidate SHA.

## Alternatives considered

**Keep serving gestaltrun.com until its filing completes.** Rejected: the filing timeline is unbounded, the user has explicitly approved the move, and production service carries filing risk meanwhile.

**Serve the new domain without moving `PLATFORM_ORIGIN` (proxy or redirect only).** Rejected: OAuth callbacks and Relay WSS must terminate on the origin the clients and listen process actually validate; redirecting OAuth POSTs or WSS indiscriminately breaks both, and the issue text forbids it.

**Replace the ALB certificate instead of attaching a second one.** Rejected while the ALB is retained: multi-certificate attachment keeps gestaltrun.com serving during staging and while old-client callback transition evidence is pending, which the rollback plan and the old-client population both depend on; the old certificate is detached only by an explicit later decision after Stage 5 evidence closes. Cost right-sizing may still select an architecture without this ALB; that is a Stage 0.5 user decision, not this staging rule.

**Treat the current two-instance/ALB architecture as fixed.** Rejected as a planning default and resolved by explicit user choice: the cost request opened the architecture decision, the single-node alternative was evaluated and not selected, and the user chose two smaller monthly `ecs.e-c1m2.large` instances with a retained two-node load balancer and optimized RDS/Redis billing. The unconditional database/identity/data preservation and the explicit gate on the pending quote and purchase remain the counterweights.

**Point `PLATFORM_ORIGIN` at the apex.** Rejected: the www hostname is the issued canonical authority; apex support exists so bare-domain HTTPS does not fail, not as a second authority. Two origins would double the CORS and callback surface for no benefit.

**Rename brand surfaces and historical docs to the new domain.** Rejected: the change is an origin migration, not a rebrand; brand name and historical URLs stay. The homepage canonical stays gestaltrun.com pending an explicit SEO decision, recorded here as undecided rather than silently switched.

**Reissue clients before the Platform serves the new origin.** Rejected: baked client authority must point at an origin that already passes `/readyz` and login, or every updated install breaks at first run.

## Risks

- DNS TTL 600 s bounds, but does not eliminate, propagation overlap: both names may resolve during a window when the OAuth App callback accepts only one origin. Stage ordering (certificate and DNS before the Environment switch) keeps every interval serveable.
- Old-client login continuity depends on both hostnames reaching the same backend with the same identity, which the verified mechanism requires; a frontend or identity change selected in Stage 0.5 that breaks that pairing breaks old-client login completion even with the old hostname serving. Login attempts pending at cutover reference the pre-switch callback and may fail to complete until the client restarts and re-initiates; the restart is a recorded transition step, not a silent loss.
- The DISABLED state of the old gestaltrun.com DNS records is an unresolved deliberate decision owned outside this note: while it persists, old clients have no direct Platform path, and only the origin-independent Desktop updater can carry an old install to the reissued release. Re-enabling is not implied by any stage here and needs its own explicit decision.
- A cheaper shape selected under the cost request can reduce high availability below the two-instance/ALB baseline: single-instance service accepts downtime during deploys and instance failure. The note does not choose that trade; it only routes the decision through the explicit user gate, and the deploy evidence records what HA was given up.
- The contradictory billing reports are resolved in direction by the timestamped corrected report (balance +86.52, no ALB financial locks, 2026-09-05T16:04Z), which supersedes the earlier FinancialLocked/−13.48 reading; the durable rule is that account state is time-sensitive input, so a current timestamped recheck is taken immediately before any mutation rather than any single report being treated as settled fact.
- The 2 vCPU/4 GiB `e-c1m2.large` shape is smaller than the current instances and its sufficiency is a validated assumption, not a measurement, until Stage 0.5 checks it against observed utilization; the 47.52 catalog figure is not the purchase amount until the disk-inclusive total is confirmed. A mis-sized shape surfaces as degraded service after replacement, which the rolling replacement bounds but does not eliminate.
- The physical Android WebView path (#480) may fail on the new certificate for reasons distinct from the old diagnosis; Stage 4 gates publication on that path, so the risk is a blocked reissue, not a broken published build.
- Two hostnames serving one product page split SEO standing; the default canonical keeps the indexed origin, at the cost of the new domain accumulating standing more slowly.
- Preserved identity means preserved blast radius: a bad Stage 3 deploy touches the same durable state the old domain served. The two-instance rolling replacement and the workflow's rollback record own this across the instance replacement; no new mechanism is added here.
- Multi-certificate listeners have quota and evaluation-order behavior on ALB; Stage 1 verification observes the actual listener state before DNS is cut, and the plan does not assume SNI behavior beyond what that observation confirms.
