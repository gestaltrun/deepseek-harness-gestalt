# Local modifications

Every divergence from the pinned upstream commit in [UPSTREAM.md](UPSTREAM.md). Product behavior belongs in `@deepseek-ai/dsh-client-ui-workbench`, not here.

1. **Workspace package manifest** — `package.json` / `tsconfig.json` / `tsconfig.dts.json` / this file / `UPSTREAM.md` are repository-owned. Upstream `package.json` name `dsh-better-sidebar` is `@deepseek-ai/dsh-client-better-sidebar`; version follows the monorepo root. `tsconfig.json` project references use this repository's package paths (`../../core/session`, not `../../session/session`). The snapshot is not a `tsconfig.client.json` project: those references would pull host `Context` merges into the client program.
2. **`src/config.ts`** — `import z from 'schemastery'` is `import z from '@deepseek-ai/schemastery'`.
3. **`src/context-types.ts`** — the snapshot imports `Context` from `@deepseek-ai/cordis` and carries its structural service face through a local `CordisContext & SidebarContextServices` intersection. The repository Cordis augmentation adds only `betterSidebar`, so snapshot mirrors cannot collide with owning package declarations.
4. **`src/invariant.ts`** — companion rewritten to the repository invariant gate (`PACKAGE_NAME` matches this workspace package).
5. **`tsdown.config.ts` / `src/client/chunk-loader.ts`** — client factory id is the workspace package name; Host/Client build faces split the Node library from the browser chunks; the plugin-registry `client-registry.js` channel is omitted; chunk and client externals request `@deepseek-ai/cordis`. The Node library build emits only snapshot sources to `lib/types` through `tsconfig.dts.json` (`noCheck` and `noResolve`) so published declarations exist without joining the client aggregate or emitting dependency declarations beside dependency sources.
6. **`src/bundle-route.ts`** — `LIB_DIR` is the package `lib/` directory, not `dirname(import.meta.url)`. Source launch (`tsx`) otherwise looks for `src/client-terminal.js` and the terminal / editor / mermaid chunks 404.
7. **`src/client/BrowserView.tsx`** — when `ctx.get('workbenchBrowser')` is published, the tab renders that official chrome. The sandboxed iframe remains the fallback for a standalone snapshot install.
8. **`src/client/service.ts`** — `setPanelOpen(open)` expands or collapses the right workbench panel. The official preview and first Agent tab use it; a type-only `openTab` does not expand.
9. **`src/client/TabBar.tsx` / `src/client/sidebar.module.css`** — under `window.dshDesktop.chromeOverlayShow`, the `+` menu opens in the Desktop native overlay view instead of the in-page `Menu`. The Desktop top Workbench aligns to the 36px Window Chrome and uses only the flexible unused space after `+` for window dragging; tab dragging temporarily returns that space to the drop target. The bottom Workbench and browser-only `dsh web` render no window drag space, and Web keeps the in-page menu and 34px tab strip.
10. **`src/client/Sidebar.tsx` / `src/client/state.ts` / `src/client/sidebar.module.css`** — right and bottom panel sizes contribute layout space only while their respective panel is visible, so resizing one axis cannot activate a closed panel's retained size. Panel resize keeps the conversation scrollbar gutter and scrolling intact but makes its thumb transparent until release, so Chromium does not flash an overlay scrollbar while the scrollport changes size.
11. **`src/client/index.tsx`** — the Desktop overlay document (`data-dsh-desktop-overlay` / `?dsh-desktop-overlay=1`) does not mount the snapshot `Sidebar` into `document.body`. Overlay Settings still use the Host chrome settings seat.
