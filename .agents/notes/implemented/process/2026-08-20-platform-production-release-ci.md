# Agent Note: Platform production-only release CI

Status: implemented

English | [中文](2026-08-20-platform-production-release-ci.zh.md)

## Problem

The Platform listen process and its GitHub Actions workflows need one operated environment. A second development origin, OAuth App, database, and identity namespace would add a staging selector and a second credential namespace that nobody will operate. Production apply must also reach private ECS instances without assigning public addresses or storing a long-lived Alibaba Cloud credential in GitHub.

## Decision

The operated Platform is production only. [`apps/platform/src/production-env.ts`](../../../../apps/platform/src/production-env.ts) names the listen-process secrets, treats an unset `PLATFORM_ENVIRONMENT` as production, and refuses any other selection before [`boot.ts`](../../../../apps/platform/src/boot.ts) loads one complete operated identity. The listen entry has no development identity or fallback credential, database, or namespace.

GitHub Actions uses Environment `production` only. [Platform Image](../../../../.github/workflows/platform-image.yml) builds on pull requests and matching master pushes, and pushes to GHCR only on `workflow_dispatch` with `inputs.push`. [Platform Deploy](../../../../.github/workflows/platform-deploy.yml) installs the locked workspace dependencies without lifecycle scripts before it validates the production and ECS names through the source-launched [`production-env-cli.ts`](../../../../apps/platform/src/production-env-cli.ts). Both jobs exchange GitHub's Environment-scoped OIDC token for a short-lived Alibaba Cloud role and verify Cloud Assistant on exactly two private ECS instance ids. The deploy job runs only when `inputs.deploy` is true.

The RAM deploy role sets `MaxSessionDuration` to at least 21,600 seconds; the credential exchange fails before any ECS operation when the role limit is lower. The deploy job pulls the private GHCR image before acquiring its six-hour Alibaba Cloud session, encrypts the runtime environment with a per-run key, and stages the image, encrypted environment, and [`platform-host-deploy.sh`](../../../../apps/platform/scripts/platform-host-deploy.sh) under one private, run-scoped OSS prefix. Six-hour signed internal URLs give temporary Cloud Assistant commands access without disclosing a GitHub token to ECS. The workflow deletes the OSS objects on every job exit; Cloud Assistant deletes each command after execution. [`platform-cloud-assistant.sh`](../../../../apps/platform/scripts/platform-cloud-assistant.sh) requires terminal invocation status and exit code zero rather than treating API acceptance as completion. Prepare commands have a thirty-minute timeout, ordinary actions have five minutes, and rollback or recovery has thirty-five minutes to wait behind an active preparation lock, bounding the remote transaction below the credential lifetime.

The workflow verifies that the configured ALB server group contains exactly the two available ECS instance ids on port 80. The host script starts and verifies a candidate on every instance before the global contract, requires a live predecessor on every instance, replaces one instance at a time while the other remains available, and restores only instances with a renamed rollback container. Every host action holds `/run/dsh-platform-deploy.lock`; rollback and independent recovery therefore wait for an active action or its Cloud Assistant timeout instead of modifying the same containers concurrently. A stable private OSS record binds the ordered instance ids and marks the deployment `rollbackable` until production HTTPS readiness succeeds, `commit-pending` through rollback cleanup and attachment-authority cutover, and `committed` after cutover. Recovery reads the complete record and constructs its instance-id JSON without pipelines, refuses changed target variables, restores predecessors for the first phase, finishes cleanup and cutover for the second, and completes final cleanup for the third, then deletes the record and run artifacts only after both instances resolve. A new deploy refuses to overwrite an unresolved record. Attachment storage uses two invocations: `postgres` establishes the atomic bridge, then `oss` requires every predecessor readiness response to report that bridge. The runner verifies the selected mode and both deployment ordinals through the production HTTPS origin and ALB before rollback cleanup. The CLI entry is not bundled into `boot.mjs`.

Desktop and Mobile parse the same single production identity and reject localhost before product work ([operated Companion Platform identity](../architecture/2026-08-22-operated-companion-platform-identity.md)). Generic environment-pair validation remains available to bounded capability tests, not product entries.

## Alternatives considered

**Operate a second development Platform.** Rejected: the product operator will not provision a second origin, OAuth App, database, or identity namespace. A staging selector would also reopen arbitrary-endpoint selection that Companion packaging already forbids.

**Keep pair validation by running development on the same hosts.** Rejected: shared hosts would collapse the identity namespaces the pair validator exists to keep apart, and the listen process would still need a development secret set.

**Validate production names with a bash checklist in the workflow only.** Rejected: the listen process and the workflow would drift. One TypeScript entry owns the names; the workflow invokes it, and tests pin both the functions and the YAML.

**Push the image on every master build.** Rejected: GHCR publication is a release mutation and stays behind explicit dispatch.

**Assign an EIP to each ECS instance and deploy with SSH.** Rejected: ALB already reaches the VPC backends. Public instance addresses and inbound administration are unrelated to serving traffic and widen the production attack surface.

**Give ECS a GitHub package token and pull GHCR directly.** Rejected: a Cloud Assistant command would carry a credential for a second control plane. The Environment-authorized runner already has package access and can stage a content-addressed image archive through private OSS.

**Store an Alibaba Cloud AccessKey in GitHub.** Rejected: GitHub OIDC and RAM can bind a short session to the repository's protected `production` Environment. A long-lived key would add rotation and leak impact without providing a required capability.

## Consequences

A missing production name fails validation without printing values. Setting `PLATFORM_ENVIRONMENT=development` fails the listen process. Image publication and ECS apply remain manual, Environment-protected steps. ECS needs no EIP, public SSH, GitHub credential, or persistent deploy command. The OIDC role needs only Cloud Assistant execution and result reads, ALB server-group reads, and access to the run-scoped OSS deployment prefix. The per-run encryption key remains inside the GitHub job and temporary command content; encrypted OSS objects and commands are deleted automatically, but Alibaba Cloud control-plane audit records remain part of the trusted production administration plane. An error or runner termination enqueues rollback on both instances; the host lock prevents that rollback from racing an action already started by Cloud Assistant. The separate `recover` dispatch uses fresh credentials and the checked-out host script when a runner disappears before its handler runs; the durable phase prevents recovery from reverting a deployment whose rollback cleanup has begun. Candidate or preflight failure leaves every predecessor active; a contract failure restores each touched predecessor and leaves an untouched instance unchanged. The listen process writes startup and error lines to container stdout/stderr; Docker `json-file` rotation (`20m` × `3` files) bounds that volume on each ECS instance. The apply step also starts LoongCollector with user-defined id `gestalt-platform` so those lines can reach SLS project `gestalt` logstore `application`. The collector reads the Aliyun account id from hardened ECS metadata at `100.100.100.200`, and falls back to Environment `production` `PLATFORM_SLS_ACCOUNT_ID` when metadata is empty.

## Testing

[`apps/platform/tests/production-env.spec.ts`](../../../../apps/platform/tests/production-env.spec.ts) pins operated-environment selection, missing-name order, ECS instance-id validation, dependency installation before the source-launched validation CLI, CLI stderr that lists names without values, OIDC permissions and pinned action identity, encrypted staging, Cloud Assistant empty-result polling and terminal-result checks, interruption cancellation, independent recovery, all-instance finalization, candidate readiness, bridge prerequisite, contract ordering, instance-specific rollback, absence of SSH names, `json-file` rotation options, and LoongCollector registration. It also pins Platform Image's master-push build without GHCR push.
