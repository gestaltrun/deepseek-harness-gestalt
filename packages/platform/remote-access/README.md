# `@deepseek-ai/dsh-remote-access`

English | [中文](README.zh.md)

Remote Access Service Definitions and Personal Pairing Service Provider. `ctx.remoteAccess` keeps Mobile Access disabled per Desktop Installation until Settings enables it, allocates two-minute endpoint mailbox routes, authenticates each Account Session's Installation id, kind, and Mobile presentation through `AccountService.currentInstallation()`, requires both Installations to resolve to the same Account, and grants a Device Principal only after explicit Desktop confirmation. Endpoint completion carries no caller-supplied device metadata; pending and confirmed records copy the authenticated Mobile Installation presentation. Open-registration quotas cap installations, pairings, and blobs; capacity watermarks reject new login, pairing, blob, or WSS attach with `PLATFORM_CAPACITY` and `retryAfter` while established ciphertext streams continue. Pairing Challenge HTTP supplies the TCP peer address and ignores `x-forwarded-for`. Hourly challenge, concurrent blob, and daily upload windows live in the shared pairing-transaction state, so two providers with one `PersonalPairingAuthorityStore` enforce one Account-complete limit. Hard caps return a 60-second `retryAfter`; sliding windows return remaining-window seconds. `admitAttachmentBlob` commits an Account quota lease with an absolute expiry before returning; every later successful pairing transaction migrates legacy reservations to a bounded lease and evicts expired leases. The operated lease duration is twice the configured attachment capability lifetime, and attachment stores reject a lease that ends before blob authority. This permits only bounded orphan overcount after an indeterminate publish and prevents active-blob undercount. `releaseAttachmentBlob` performs eager cleanup without storing ciphertext. Development and production keep separate origins, OAuth Apps, callbacks, credentials, databases, and identity namespaces; secrets come from deployment-managed references and fail closed when missing. `PersonalPairingAuthorityStore` atomically owns shared Desktop route association, endpoint mailbox, prepared publication and compensation records, confirmed Mobile results, and quota windows; the memory adapter is a deterministic test adapter, while deployment supplies one durable adapter to every Platform Instance.

Platform returns routing metadata containing no invitation PSK. Desktop creates the full XKpsk3 QR or HTTPS payload locally, retains its private state in protected storage, and sends only opaque handshake messages plus endpoint public-key digests through Platform. A completed handshake remains pending while both Installations display the same six authentication words derived from their local transcript. A completion id replays only when a retained SHA-256 commitment matches the Account, Mobile Installation, complete invitation, and Mobile handshake bytes; changed request content fails as an id collision. The shared transaction document uses format version 1. An unversioned document retains digest-bound replay and confirmed pairings; completion or pending records without a digest become non-replayable terminal cleanup records. Unknown explicit versions and malformed versioned records are rejected. Confirmation ids make confirmation retries idempotent, and serialized mutation gives one concurrent completion the routing challenge.

Terminal state is committed before cleanup. Each authenticated Installation may own at most four live challenges, four pending pairings, and sixteen total live or replay-retained lifecycle records. Cleaned replay projections expire after five minutes, while cleanup-failed tombstones retain capacity until destruction succeeds. Endpoint publication is generation-bound and durable before Relay registration; rejection, expiry, disablement, failed publication, and explicit Personal Pairing revocation move both credential digests and the confirmed-Mobile result into a stepwise compensation record before authority changes. Each credential revoke, Mobile-authority deletion, and stored-pairing cleanup step commits independently, so another Platform process resumes cleanup after a crash without losing the digests. Endpoint mutations fail before changing state unless Relay supplies both registration and revocation. Provider disposal preserves confirmed pairing and route authority so rolling replacement can reconnect; explicit disable owns durable revocation.

The product endpoint flow keeps its XKpsk3 adapter, invitation PSK, P-256 private credentials, and reconnect state on Desktop and Mobile. Platform stores only opaque mailbox messages, expiration and idempotency metadata, route generation, pairing-scoped public-key digests, and compensation progress. Confirmation rejects equal or reused endpoint digests and publishes both atomically under one selector. Desktop protected storage admits at most sixteen retained active or pending pairings before publication; sleep, window close, and ordinary quit quiesce Relay without deleting that vault. Mobile commits the opened sealed authority and reconnect state before erasing one-shot invitation state. A process restart resumes the same transaction or starts Relay from the committed grant without reopening it. Account changes await the previous Account's Companion release and Relay revocation before activation continues. Mobile unpair authenticates the current Mobile Installation and durably revokes its own confirmed pairing, Device Principal, and both Relay credentials at Platform before the UI reports ready. It also attempts handshake, pairing-key, Companion, and Relay cleanup independently and reports all failures; a rejected cleanup remains an explicit retryable failure reported by the React owner. Both controllers stop timers, drain in-flight work including browser-camera scanning, and reject pairing operations after sign-out or unmount. The resulting Device Principal has only `companion-surface` authority. The development keyless adapter remains test-only and is absent from operated Platform composition and product snapshots.

`ctx.remoteRelay` owns the stateless multi-instance Relay lifecycle. Desktop and Mobile retain independent P-256 signing credentials while the persistent `RelayRouteStore` retains only public-key digests. Every physical connection proves a fresh route-, endpoint-, attachment-, and expiry-bound challenge, so an observed attach exchange cannot authorize another connection and the opaque route id alone cannot attach. The Personal Pairing authority binds the Mobile public-key digest's content-free fingerprint to the confirmed device. Each authenticated Mobile attachment records its connection token and expiring lease; attach, heartbeat, and ciphertext access advance `lastAccessAt`, while close removes only that token. Presence is true when any current lease remains, so a stale close cannot clear a replacement and a crashed process becomes offline at lease expiry. Desktop Settings reads this state rather than a fixed confirmation-time value. Each Platform Instance authorizes an attachment, flushes ready, then registers it in an expiring shared directory and publishes directly to the target instance. Cross-instance events contain only bounded Relay ciphertext, branded transport ids, connection tokens, and route revision. A missing target returns `REMOTE_OFFLINE`; there is no offline ciphertext or mutation queue. Capacity sheds only new attachments, slow consumers are disconnected at a configured byte bound, heartbeat revalidates route authority, and rotation or revocation invalidates older live attachments across instances. The host-only `relay-provider` bundle imports `RemoteRelayError` from this package's public entry so HTTP Consumers that map that class share one constructor.

Persistent deployment state is limited to route identity, credential digest, monotonic revision, and revocation/association state. Ephemeral coordination is limited to expiring attachment locations, invalidation events, and direct ciphertext Pub/Sub. Instance exit closes its sockets; Mobile and Desktop acquire a fresh non-sticky connection, and Desktop sends an authoritative encrypted resynchronization instead of migrating a live socket. Every capacity, directory, heartbeat, buffer, connection, and attach timeout is an explicit validated composition value.

#### KV Cache effect

None.

## Known Limitations and Deferred Work

- Product composition assembles the endpoint-only mailbox, durable authority stores, sealed Mobile authority, and Snow channel. Independent security review and WKWebView/Android WebView device evidence remain release evidence rather than runtime feature switches.
- Operated Platform persists mailbox, publication, pairing-to-route, and Relay digest authority through PostgreSQL and uses Redis only for expiring attachment discovery and ciphertext delivery. This repository does not provision PostgreSQL, Redis, TLS, or cloud instances.
- Product Desktop and Mobile use the endpoint-owned Snow mailbox and Companion channel; Platform mounts no pairing cryptography. Physical WebView evidence and independent review of the exact implementation remain release blockers.
