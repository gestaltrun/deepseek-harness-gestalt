# Agent Note: Host-owned member-question receiver ledger

Status: implemented

English | [中文](2026-08-31-host-owned-member-question-receiver-ledger.zh.md)

## Problem

The first receiving implementation derived `mq-recv:<originSessionId>::<member>` in the browser and kept pending and terminal state only in `ReceivingQuestionBook`. That let the composite card render, but reconnect, process restart, multiple Installations, and an explicit human turn had no Host authority. A browser countdown could decide expiry, a later frame could revive a locally forgotten pending card, and materializing a real Session required callers to coordinate Session creation and prompt admission as two separately retryable operations.

## Decision

`@deepseek-ai/dsh-member-question-receiver` owns receiver authority on the Host. Its Service Definition exposes five deep operations: authenticated `ingest`, complete `snapshot` plus a change feed, terminal `settle`, single-call `admitHumanTurn`, and exact Account/Project Workspace `bind` plus `resolve`. The file Provider and authenticated-ingress Consumer adapter remain folded into this package because the current delivery has one storage mechanism and one endpoint callback concern; splitting three packages would add no independently evolving role.

`ingest` accepts receiver Account authority beside the decoded encrypted operation. The authority comes from the authenticated endpoint and is absent from member-question plaintext. One route `(originSessionId, receiving Account)` receives a Host-generated opaque `ReceivingSessionId` persisted on first arrival. Payload content cannot select another account, and no Host identity is assembled from the renderer's `mq-recv` spelling.

The Decision Brief remains on each question's `member-question` intent rather than on a sibling request frame. A forwarded item is therefore self-contained, while the Host receiver snapshot adds only authority-owned routing, revision, and terminal fields.

The environment ledger is the authority for pending and terminal projections and local Workspace association. It stores the bounded Decision Brief fields admitted by the Companion codec, reference path/reason metadata, routing identities, terminal metadata, the exact Workspace id selected for each Account/Project pair, and each reserved human action as text plus durable attachment references under its request digest. Referenced document bodies and raw browser image bytes are absent. Startup validates the complete document through the current Companion codec and fails on a foreign format, malformed record, duplicate binding, dangling reference, inconsistent terminal, or mismatched admission digest.

One serialized transaction owner enforces publication order. Idempotent arrival returns the recorded identity. Before a newer same-route question becomes pending, the previous pending question's `expired` or `superseded` candidate passes through the injected global first-claim authority and the canonical retained terminal commits to the ledger. Decline is a human terminal distinct from initiator withdrawal and carries the winning `InstallationId`, device name, and settlement epoch. A losing local claim commits the returned canonical terminal instead of the candidate. Change listeners observe only post-commit complete projections, and callback exceptions are contained.

The Host clock and one earliest-deadline scheduler decide expiry. The scheduler first claims the terminal, then persists it; a publication or file failure leaves the pending row retryable. Startup settles every overdue pending row before reads become available, so reopening cannot revive an expired question. Disposal closes notification and timer admission, then waits for the transaction tail without clearing durable state.

The shipped Web Host mounts the receiver and exposes exact `memberQuestion.workspaceBinding`, `memberQuestion.ensureWorkspaceBinding`, `memberQuestion.bindWorkspace`, `memberQuestion.snapshot`, and `memberQuestion.settle` RPCs plus a complete `host/member-question-snapshot` baseline/change frame. Project creation derives its bound remote from the normalized `origin` of the exact local Workspace; arbitrary surface input cannot select another remote. Project creation and invitation acceptance commit the exact authenticated Account, Project, and local Workspace id through the binding RPC; the RPC first proves that Workspace is still registered. Platform invitation acceptance follows only after the local commit. Settings recovery resolves the current Account's unique Project by the Workspace origin and asks the Host to ensure the persisted exact binding. The Host retains a live binding, atomically repairs a missing or stale binding through compare-and-bind, and returns a different live checkout as a conflict; concurrent recovery therefore cannot migrate the first live winner merely because both checkouts share an origin. Binding validation and commit share the Workspace registry mutation order with create and delete, so an accepted candidate remains live through its durable commit. Settlement validates the persisted `ReceivingSessionId`, revision, and question id, and uses the Host Installation identity; a missing receiver, stale tuple, unresolved binding, or missing identity fails loud. Development may opt into a keyless local terminal authority, while production remains deferred and fail-closed until authenticated cross-machine publication is composed.

`ReceivingQuestionBook` projects only higher-revision Host frames into identity-stable receiving Session faces under the persisted Host id. Disconnect retains the last projection, and reconnect replaces it from a complete baseline without losing pending or terminal records. The Client sends answers and declines through the Host RPC; expiry, supersession, withdrawal, and canonical terminal winners come only from the Host. Terminal records remain public in the conversation snapshot, and a Client whose Installation differs from the winning answer derives `answered-elsewhere` with the winning device name and settlement time. Before materialization the only prompt route is `memberQuestion.admitHumanTurn`; a later snapshot carrying `hostSessionId` binds that same face to the ordinary Host Session.

`admitHumanTurn({ receivingSessionId, revision, rpcId, content, mode })` is the only materialization interface. The API Proxy first promotes browser images through the ordinary attachment service, then the receiver durably reserves `rpcId`, normalized content, mode, and digest before calling the high-level adapter. While holding its transaction, the receiver resolves the persisted Account/Project binding and passes the exact local Workspace id in the admission context; the adapter never queries the receiver service reentrantly. The adapter reuses the opaque receiving id as the Host `SessionId`, attaches the Workspace, appends ignorable `member-question/received` and `member-question/settled` records, injects each bounded brief with a stable plugin message id, admits the stable human message, and flushes the ordinary Session log. Success commits materialization and admission after the adapter returns. Failure preserves the reservation; retry must carry the same action and `rpcId`, while stable Session/message identities and the log detect completed stages. This closes the crash interval between adapter success and ledger commit without exposing `session.create` followed by `prompt` to callers. Arrival never invokes the adapter.

## Alternatives considered

**Keep `ReceivingQuestionBook` authoritative and persist it in browser storage.** Rejected because the browser does not own authenticated Account authority, global first claim, process restart, Host Session materialization, or the clock that can disable every Installation consistently.

**Create a Host Session at question arrival.** Rejected because arrival is a collaboration notification, not human intent to run the local agent. Creating the Session and agent eagerly would weaken the zero-model guarantee and add empty durable conversations for ignored questions.

**Expose `createReceivingSession()` and `prompt()` separately.** Rejected because a crash or retry between the calls can create duplicate Sessions, lose the first human message, or admit it twice. One high-level adapter under a durable `rpcId` reservation owns both actions.

**Store referenced document bodies or raw browser image bytes in the receiver ledger.** Rejected because Companion document transfer and the attachment service own those bytes. Crash-safe admission retains only the bounded human text and durable attachment references required to replay the reserved action.

**Treat the renderer countdown as expiry authority.** Rejected because suspended or disconnected renderers cannot settle a global state and can disagree across Installations. The Host clock, canonical terminal authority, and durable commit establish one outcome.

**Carry the Decision Brief beside `question/requested`.** Rejected because fields on the item intent keep any forwarded question self-contained and avoid a second encoding of the same sender payload.

## Consequences

Receiver state survives Host restart and exposes one authoritative pending/terminal projection with stable Host identities. Same-route replacement, expiry, answer, decline, and cross-device winners commit in one order. Browser reload and reconnect preserve the same ids and records without creating a Host Session or model path. Generic and plan-review questions retain their existing Host-session flow.

Explicit human admission is retryable without a two-hop client protocol, and the Web Host mounts the adapter through the API Proxy. Workspace selection survives Host restart and never resolves by display-title guessing. Cross-machine first-claim publication remains injected until the project-registry transport exists, so production transitions requiring it fail closed. The file format is pre-release version `1` and has no compatibility shim.
