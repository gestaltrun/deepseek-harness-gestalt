# Agent Note: Mount a local two-instance companion Platform for product clients

Status: implemented

English | [中文](2026-08-21-local-companion-platform.zh.md)

## Problem

Production Platform listen mounts Account HTTP and migrates Remote Access tables, but pairing HTTP and Relay WSS stay unmounted until independent Noise review. Assembled keyless fixtures already prove pairing and two-instance Relay in process, yet Mobile and Desktop product entries have no loopback composition that shares one trusted HTTPS origin, real Account sessions, and a non-sticky TLS front. Simulator browsers also cannot complete GitHub login when Capacitor Browser is absent unless a still-valid pending attempt can resume after navigating the current browsing context.

## Decision

[`examples/local-companion-platform`](../../../../examples/local-companion-platform/README.md) is the long-running development listen. It binds one `127.0.0.1` TLS endpoint, alternates `/v1/*` and Relay upgrades across two in-process instances, and shares memory Account, pairing-authority, and Relay route stores. The selected development identity is that TLS origin; production identities remain the operated `www.gestaltrun.com` pair so client pair validation still rejects a shared identity. GitHub authorization in this composition is `/v1/account/oauth/github/development-complete` on the same origin and always yields the `octocat` public identity. Desktop completes that loopback URL in-process and does not follow the 303 page return. Desktop loopback Fetch uses Node `https.request` and an in-memory Response, because constructing a Chromium `Request`, `Response`, or `Headers` in the Electron main process deadlocks a renderer that is waiting on the Settings invoke. The Host admits `beginLogin` without holding that invoke across Account HTTP. Loopback development persists the Account record as owner-only file bytes because `safeStorage.encryptString` blocks the Host during authorization. `LOCAL_COMPANION_PAGE_ORIGIN` reverse-proxies non-`/v1` paths to Mobile Vite so the browsing context can share the TLS origin, and the TLS front rewrites that Vite origin onto the selected HTTPS origin for Account and pairing CORS when a client can present the bundled certificate. An Android WebView that cannot complete TLS to that certificate opens the Vite origin instead: Mobile Vite proxies `/v1` (including Relay WebSocket) to the listen with certificate verification disabled, and the Mobile entry rewrites Account, pairing, authorization, and Relay URLs onto that page origin. Pairing links still print the selected HTTPS origin. [`apps/platform/src/boot.ts`](../../../../apps/platform/src/boot.ts) does not import this example or `DevelopmentKeylessPairingHandshakeProvider`.

`PlatformAccountInstallation.load()` resumes a still-valid pending login as polling when no session exists and clears an expired pending attempt. A non-native Mobile entry `location.assign`s the prepared authorization URL so `load()` can continue after return; only a packaged Capacitor WebView uses `Browser.open`. The entry still has no `window.open`, popup, or custom-URL token fallback. Default Account and Remote Access Fetch implementations stay bound to the global so browsers can call them.

The Loader scenario uses sequential entropy and the real Desktop/Mobile Account clients plus Remote Access HTTP and WSS clients to prove same-account login, default-disabled Mobile Access, confirmed pairing, and one encrypted Relay round trip.

Keyless product Desktop and Mobile share the Relay attachment ids `desktop-development-keyless` and `mobile-development-keyless`. A one-byte inbound frame is the development sync announcement; longer frames are sealed Encrypted Companion messages. Desktop confirms `create-session`, `submit-prompt`, `cancel-prompt`, `offer-attachment`, `settle-approval`, `answer-ask-user`, and `query-operation-status` from an in-process development authority. A prompt first projects the user line with `streaming: true`, then after two seconds projects the assistant line plus pending approval and Ask User cards unless cancelled. Mobile updates the browse list and conversation only after that confirmation or projection, can name a first Workspace, refuses composer mutations while Remote Offline, restores Desktop-confirmed Session metadata from Companion Cache, and offers each Desktop-authorized settlement decision. The Mobile browse connection label follows `companionMayMutate`.

## Alternatives considered

**Mount pairing and Relay on production listen.** That would ship an unreviewed handshake on the operated origin. The production process stays fail-closed.

**Change the selected Platform origin to `http://127.0.0.1`.** Account and Remote Access HTTP allow only the selected HTTPS origin, and pairing links must stay `https:`. The selected identity remains the TLS listen; only page-origin traffic is rewritten through Vite.

**Keep pending login only in process memory.** Same-window authorization would lose the five-minute attempt. Resuming durable pending state is the product recovery path, not a test hook.

## Consequences

Developers can stand up one loopback origin that Mobile simulators and Desktop keyless flags consume without a second cloud Platform. The trade-off is an unreviewed handshake, memory stores, and a bundled test certificate: this listen is not production and cannot replace Noise review, SLS, or TestFlight/APK acceptance.
